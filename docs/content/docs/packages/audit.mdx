**Status:** built, order 13. **Design from:** new. Neither reference project has one (both were searched).

## What it is

`@repo/audit` records the actions somebody may later have to explain: a till void, a refund, a change to a fee, a staff member opening a child's record, a platform admin impersonating a user to help with a support ticket.

## Requirements

- **Append-only, enforced by the database.** An application bug, a script or an admin must not be able to edit or delete a row.
- Every entry says who (a user, the system, or an admin acting as a user), what, on which record, in which organization, and when.
- **No personal data in the details**: ids only, never names, notes or amounts that identify a person.
- Cheap to write, and quick to read for one organization or one record.
- Written in the same transaction as the change it describes.
- Retention can differ by organization and by kind of record (childcare records have retention rules; so does a till).

## Design

- **Where things live.** `@repo/db` already says tables live in `packages/db/src/schemas/<name>.ts`, one file each, so there is one migration history. The `audit_log` table therefore lives there, and `@repo/audit` holds the behaviour: the action catalog, the writer, the reader. It needs only `@repo/db` and `zod`.
- **The table**, `audit_log`: UUIDv7 `id`, `occurred_at` (`timestamptz`), `organization_id` (null for platform-level actions), `actor_type` (`user`, `system`, `admin`) with `actor_id`, `acting_as_id` (set when an admin impersonates), `action`, `target_type` with `target_id`, `request_id` and a `details` JSON. CHECK constraints enforce the shape in Postgres, not just in TypeScript: the action name format; a `system` actor has no id and the others do; `acting_as_id` only for admins; target type and id come together.
- **Postgres refuses changes.** A trigger raises an error on any UPDATE, DELETE or TRUNCATE. It is a hand-written migration (`drizzle-kit generate --custom`), because Drizzle does not describe triggers. The trigger stops bugs, scripts and a careless admin; it does **not** stop a superuser, who can disable it. The real boundary is the database role: the API connects as a role that has `INSERT` and `SELECT` on the table and nothing else. That is a deployment setting (the role name differs per host), described in the README and the hosting docs.
- **A catalog of actions.** `defineAuditActions({ "till.void": z.strictObject({ sale_id: z.uuid() }) })` says which actions exist and what each one's details are. `createAuditor({ actions })` returns a `record(executor, entry)` typed by that catalog, so a typo in the action name or a missing or extra detail field fails to compile. The package ships only the generic actions (an admin starting and stopping impersonation); each platform adds its own beside its own code.
- **Ids only in the details, enforced three ways.** The catalog's schema is `strictObject`, so unknown fields are rejected. Values must be flat (a string, number, boolean or null; no nested objects). And a runtime guard refuses any string with a space, an `@` or more than 64 characters, because prose and email addresses have those and ids and codes do not. The guard cannot catch a single-word name, which is why the types matter: do not add a `name` field to an action.
- **Same transaction.** `record` takes either the database or a transaction, so the entry and the change commit or roll back together: never a change without its entry, never an entry without its change.
- **Reading.** `readAudit(db, filter)` returns entries for an organization, a target or an actor, newest first, with keyset pagination (`before` the last seen id) so deep pages stay fast. Indexes match those three filters. Whether the caller may read is the API's job, checked against their role in that organization.
- **Not wired into the API yet.** No route changes anything worth auditing today. The first one that does (auth, payments) calls `record` inside its transaction.

## Depends on, and the auth order

It records the organization as a plain id; the foreign key to the `organization` table is added by auth's migration, because auth is built after this package.

## Trade-offs

- Every audited write is one more insert in the same transaction. The audited actions are rare compared with ordinary reads, so the cost is small.
- Ids only in the details means an investigation looks up names separately, and an erased person's entries become anonymous, which is the intended privacy outcome.
- **Retention is not built here.** The trigger also blocks the retention job, by design. The way out is monthly partitions (dropping a whole expired partition is not a row DELETE), added with the `jobs` package and a maintenance role, once there is volume and a rule to follow. Turning a plain table into a partitioned one later means copying it, which is a known cost accepted for now: neither the volume nor the retention rule is known yet.
- A superuser can still bypass the trigger (see above). Offsite copies and database-level audit logging are hosting concerns.
