# Database: plan

## Requirements
- Products handle money (till totals, payments, invoices) and children's records, so writes need **real transactions** and the database itself must refuse bad data.
- Runs the same on a developer's Docker Postgres and on a managed Postgres (RDS, Neon, Supabase).
- A stuck or restarted database must fail one request, not hang or crash the whole API.
- Tests run against a real Postgres, never against a mock.

## Design
`@repo/db` owns the client, the column helpers, the migration tooling and the test helper. It has **no tables**: the first ones arrive with auth, and each platform adds its own.

- **Driver: `pg` (node-postgres) with a `Pool`.** The serverless HTTP drivers (Neon `neon-http`) cannot run multi-statement transactions and tie the project to one vendor, so they are out.
- **Pool limits and timeouts** (max 10 connections, 5 s to connect, 30 s idle, 15 s per statement) so a stuck database fails a request quickly. An idle-connection error listener stops a database restart from crashing the process. `pingDatabase()` gives the API a fast readiness probe and `closeDb()` a clean shutdown.
- **Helpers in `columns.ts`:** `id()` is a `uuidv7()` generated by Postgres 18 (time-ordered, so inserts stay fast), and `createdAt()` / `updatedAt()` are `timestamptz`.
- **`oneOf()` in `checks.ts`:** enum-like text columns get a CHECK constraint, so Postgres refuses a bad value from any writer, not only from code that goes through Drizzle.
- **`createTestDatabase()`** makes a throwaway database, applies the real migrations and hands back a `drop()`, so integration tests never touch real data and never collide.
- **Drizzle stays on the stable `0.45.x` line.** The v1 line is still beta/rc with a different migration format. Revisit when v1 is stable.

## Where commands get `DATABASE_URL`
One path, not two. Every database command (`db:generate`, `db:migrate`, `db:studio`, tests) reads the root `.env`, loaded by `loadRootEnv()` from `@repo/env`. That file comes from either:

- `pnpm setup:local`: disposable local values (Docker Postgres), or
- `pnpm env:pull <dev|test|staging|prod>`: the real values from Infisical.

Variables already set in the shell win over the file, so CI and production deploys pass `DATABASE_URL` directly (for example through `infisical run`) and need no file.

## Trade-offs
- Secrets from `env:pull` sit in a git-ignored, owner-only `.env` on the developer's machine. The alternative (`infisical run` in front of every command) keeps them off disk but needs two script sets, one for Infisical and one for local. We chose one path.
- The package ships without a table, so `drizzle-kit generate` has nothing to do yet. The integration test builds a table from the helpers and applies it to a real Postgres, so the helpers are still proven.

## Found while building
- **drizzle-kit on the stable line writes CHECK values as `$1, $2`** into a migration, which Postgres rejects. `oneOf()` therefore writes escaped literals; a unit test pins the SQL and an integration test applies it.
- **drizzle-kit loads its config as CommonJS**, where `import.meta` does not exist. `loadRootEnv()` finds the repo root by walking up from the working directory instead.
- **Zero tables:** `createTestDatabase()` skips migrating until the first migration exists (`migrations/meta/_journal.json`), then applies them all.

## Scale
One Postgres, one writer, strong consistency. Pool size 10 per API process. If reads outgrow it, add a read replica and a second pool; do not shard until a single instance is measurably too small.
