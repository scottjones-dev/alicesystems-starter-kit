## What this page is

The template is a base for several products: a **money manager**, a **nursery and childcare platform**, a **field service platform** and a **pub POS and management system**. Each product reuses the same packages, so a package earns its place only if at least two of them need it. This page lists every package, in build order, with where its design comes from.

Every package follows the same rules: it lives under `packages/`, keeps its code in `src/`, has a README (what, why, how to use, tests, dependencies), has tests for its logic, reads configuration only through `@repo/env`, and has a plan page here written **before** it is built.

## Planned, in build order

You asked for **auth second last and storage last**. Everything else comes before them, in this order:

| # | Package | What it will do | Design from |
| --- | --- | --- | --- |
| 12 | [`money`](/docs/packages/money) | Exact money maths in whole minor units: split, VAT, allocate | new |
| 13 | [`audit`](/docs/packages/audit) | Append-only audit log of who did what | new |
| 14 | [`jobs`](/docs/packages/jobs) | Background jobs and schedules | new (starter-kit has one cleanup job) |
| 15 | [`payments`](/docs/packages/payments) | Tenants collecting money: cards and direct debit, webhooks | new |
| 16 | [`documents`](/docs/packages/documents) | PDF and CSV: invoices, statements, reports | new |
| 17 | [`auth`](/docs/packages/auth) | Better Auth: organizations, admin, 2FA, passkeys, Expo, Stripe billing | starter-kit, plus organizations from next-forge |
| 18 | [`storage`](/docs/packages/storage) | Private object storage with presigned uploads | starter-kit |

Packages 12 to 16 are proposals: each gets a comparison of the two reference projects (where they have one) and your sign-off before it is built, as the first eleven did.

**A cost of this order.** `audit` and `payments` record which organization an action belongs to, but the organization table arrives with auth. Until then they store the organization as a plain id, and auth's migration adds the foreign keys. If you would rather have a real foreign key from the start, move auth up to just before `audit`.

## Which product needs what

"Likely" means the product will probably use it; it is not decided until that product is planned.

| Package | Money manager | Nursery | Field service | Pub POS |
| --- | --- | --- | --- | --- |
| `money` | yes | yes (fees, invoices) | yes (quotes, invoices) | yes (VAT, tips, split bills) |
| `audit` | yes | yes (access to children's records) | yes | yes (voids, refunds) |
| `jobs` | yes | yes (reminders, invoice runs) | yes | yes (end-of-day reports) |
| `payments` | no | yes (direct debit) | yes | yes (cards) |
| `documents` | yes (statements) | yes (invoices, reports) | yes (quotes, job sheets) | yes (Z-reports) |
| `storage` | likely (receipts) | yes (photos) | yes (job photos, signatures) | likely (menu images) |
| `realtime` | no | likely | yes (dispatch) | yes (kitchen screens) |
| `sync` (offline) | no | likely | yes | yes |
| `banking` | yes | no | no | no |

## How they depend on each other

```txt
typescript-config   env   errors   config
        \            |       |       |
         `-------- db   internationalization
                     \        |
                      emails ---- notifications
                                      |
      analytics   ui   observability  money   audit   jobs   payments   documents
                                      |
                                    auth  ───▶  storage
```

Everything on the left depends on nothing to its right, so the order above always builds.
